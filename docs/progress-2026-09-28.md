## Langkah berikutnya

Pada 1 Oktober, DVWA dinyalakan kembali dan ZAP Baseline Scan dijalankan pada
jaringan Docker lokal. Pemindaian pasif tanpa autentikasi menjangkau 10 URL,
menghasilkan 13 peringatan umum, 54 PASS, dan nol FAIL. Login diperlukan untuk
mencapai modul SQLi, sehingga angka tersebut bukan hasil uji SQLi.

Rincian dan batas interpretasi hasil ada di
[`zap-baseline-2026-10-01.md`](zap-baseline-2026-10-01.md). Laporan HTML/JSON
serta `zap.yaml` tersimpan lokal di `results/zap/` dan dikecualikan dari Git.

Setelah database sampel diinisialisasi ulang, smoke test proyek memverifikasi
login dan keempat level pada sesi DVWA yang diuji. Catatan crawl ZAP saat itu
sempat menyebut autentikasi form dengan token CSRF `user_token` dan 41 URL.
Namun, verifikasi lanjutan pada 1 Oktober tidak menemukan indikator login pada
sesi ZAP. Karena itu, klaim autentikasi dan cakupan crawl tersebut belum
terverifikasi dan tidak boleh dipakai sebagai hasil crawl terautentikasi.
Laporan passive scan yang tersimpan hanya dapat diperlakukan sebagai observasi
pasif dengan status autentikasi yang belum terbukti; tidak ada active scan atau
payload SQLi. Validasi form mengonfirmasi injection point dasar menggunakan GET
parameter `id`. Rincian koreksi ada di
[`zap-baseline-2026-10-01.md`](zap-baseline-2026-10-01.md).

Ground truth kemudian divalidasi black-box untuk 12 skenario × 3 replikasi.
Low, Medium, dan High memberi sinyal error, boolean, serta waktu pada seluruh
replikasi; Impossible tidak memberi sinyal dan menjadi kontrol negatif. Peta
input berubah per level, khususnya dua helper popup pada High. Rincian ada di
[`ground-truth-2026-10-01.md`](ground-truth-2026-10-01.md).

Plan discovery ZAP memasukkan dua helper High, memakai browser authentication,
memverifikasi level pada sesi scanner, dan gagal jika statistik autentikasi
tidak membuktikan login. Run Low, Medium, High, dan Impossible berhasil pada
1 Oktober: tes level serta autentikasi lulus dan kedua helper dijangkau. Hasil
ini membuktikan alur discovery, bukan keberhasilan deteksi SQLi: pemindaian yang
dijalankan hanya passive scan dan tidak mengirim payload SQLi. Laporan juga
belum menjadi pengukuran FPR.

## Pembaruan 2 Oktober 2026: smoke run validation loop

Runner lokal menjalankan satu replikasi skenario S1 (Low, error-based) dengan
kandidat manual `manual-s1-quote`. Login dan pemilihan level dilakukan oleh
runner pada sesi DVWA yang sama. Respons kandidat berstatus HTTP 200 dan memuat
indikator `database_exception` serta `sql_syntax`; baseline benign tidak
memuat indikator tersebut. Klasifikasi otomatis mencatat sinyal positif/TP
sementara, dengan `human_validation=pending`.

Log JSONL mentah tersimpan di `results/raw/` (diabaikan Git). Ini hanya
memastikan jalur runner, deteksi awal, dan pencatatan bekerja untuk S1; hasil
manual satu kali ini bukan data PSR/FPR dan belum menggantikan eksperimen formal.

## Pembaruan 2 Oktober 2026: pemasok kandidat

Ditambahkan normalizer batch kandidat LLM/SecLists. Untuk SecLists, normalizer
memeriksa format commit SHA serta memverifikasi SHA-256 file, nomor baris, dan
kecocokan payload.
Untuk LLM, normalizer meminta identitas model, versi prompt, temperatur, seed,
serta metadata knowledge base/chunk yang sesuai dengan kondisi RAG. Provenance
diteruskan ke setiap baris log validation loop. Petunjuk dan kontrak batch ada
di [`candidate-sources.md`](candidate-sources.md) dan
[`../schemas/candidate-batch.schema.json`](../schemas/candidate-batch.schema.json).

Pipeline knowledge base dan generator lokal kini tersedia sebagai kode:
`build_knowledge_base.py` membaca PDF secara read-only, memakai embedding
Ollama `nomic-embed-text`, lalu menulis ChromaDB lokal; `retrieve_knowledge.py`
menyimpan ID dan isi chunk; `generate_candidate_batch.py` memanggil Qwen lokal
dan menyimpan provenance serta audit prompt. Belum ada komponen ini yang
dijalankan. Model, paket ChromaDB, dan corpus lokal perlu tersedia sebelum
runtime RAG dapat diverifikasi. Adapter SecLists memerlukan checkout dan file
list lokal yang versinya dicatat.

Skrip pipeline lokal saat ini mengorkestrasi Ollama dan Chroma melalui API
langsung. Notebook `notebooks/colab_langchain_setup.ipynb` menggunakan
integrasi LangChain untuk mengindeks PDF yang diunggah ke Google Drive,
menjalankan smoke retrieval, dan menyimpan snapshot Chroma ZIP beserta manifest
hash sumber/config. Chroma aktif dibuka dari disk runtime `/content`; snapshot
ZIP dipulihkan dari Drive agar SQLite tidak menulis langsung ke Drive.
Notebook, indexing, dan generator LangChain belum dijalankan di runtime Colab.
Notebook kini memuat runner tunnel bertoken untuk membaca batch dari Drive,
memverifikasi login/level DVWA, dan menulis JSONL tanpa rahasia. Runner belum
dijalankan di Colab; hasilnya masih memerlukan review manusia.
