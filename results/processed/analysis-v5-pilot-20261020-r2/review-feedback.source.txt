**2. Temuan yang perlu diperjelas sebelum eksekusi**

**F-01 — Aturan “menyentuh 768 token” terlalu luas jika dianggap bukti output terpotong.**

Dokumen menyatakan semua output yang menyentuh batas 768 menjadi analysis error. Padahal, jumlah token mencapai batas **belum dengan sendirinya membuktikan JSON tidak lengkap**.

Pilihan perbaikannya:

- Bedakan `done_reason=length` atau keluaran tidak selesai dari keluaran lengkap yang selesai tepat pada batas.
- Jika memang sengaja menolak semua keluaran yang mencapai 768 sebagai kebijakan konservatif, namai sebagai **penolakan karena batas anggaran**, bukan otomatis “JSON terpotong”.

Ini berpengaruh langsung pada skor. Jika diperjelas sekarang, lakukan melalui versi protokol baru sebelum inferensi.

**F-02 — Batas antara kesalahan struktur dan kesalahan makna perlu dinyatakan lebih tegas.**

Dokumen membedakan referensi observasi tidak dikenal sebagai error, sementara citation yang bertentangan menjadi warning. Pembedaan itu masuk akal, tetapi sebaiknya ditulis eksplisit:

| Kondisi | Perlakuan |
|---|---|
| ID observasi tidak ada pada kasus | Analysis error |
| ID ada, tetapi tidak mendukung klaim | Warning semantik; verdict mentah tetap dinilai |
| `reason_code` sesuai decision tetapi decision salah | Konsisten secara internal, tetapi keputusan tetap salah |
| Trial assessment hilang/ganda | Nol untuk trial terkait sesuai aturan, dengan penyebut tetap |

**“Reason-code accuracy” juga perlu dibedakan dari “reason-code consistency”.** Pengalaman v2 sudah menunjukkan kode bisa konsisten dengan keputusan yang keliru.

**3. Batas cakupan kasus yang perlu dicatat, bukan alasan mengganti label**

- **`pilot-037/039/041`:** runtime invalid selalu disertai observasi kosong. Kasus ini belum membuktikan gate menolak runtime invalid ketika observasinya lengkap dan tampak positif.
- **`pilot-038/040/042`:** flag baseline invalid selalu sejalan dengan diagnostik baseline. Kasus ini belum menguji input yang kontradiktif, misalnya flag valid tetapi baseline memuat diagnostik. Jika konsistensi tersebut dijamin upstream, tuliskan batas tanggung jawabnya.
- **`pilot-013–016`:** empat kasus positif boolean terutama memvariasikan pola HTTP 200/404. Berguna untuk menguji kepatuhan aturan status, tetapi cakupan mekanismenya sempit.
- **`pilot-032`:** menggabungkan diagnostik kontrol dan delta negatif dalam satu kasus. Labelnya benar, tetapi diagnosis penyebab kegagalan harus melihat asesmen trial, bukan verdict saja.

Tidak wajib memperbesar pilot untuk menutup semuanya. Cukup jangan mengklaim pengujian gate atau variasi bukti sudah menyeluruh.
